## Objective and evidence boundary

The production caller must never copy expected bindings from the grant record or terminal. It must construct and cross-check them from a frozen manifest, approval and review report, the anchored filesystem root, the independently read watchdog claim, and a contemporaneous watchdog/child process observation retained before grant delivery. A raw hash establishes byte continuity; it does not establish that a proposed mechanism is scientifically true or that a caller's fields came from an independent source. This work is methods-control provenance, not a result from the Cascaded Tanks benchmark.

The current manifest has an eight-path source roster, with only five corresponding static reviewed hashes; runner, forecast and scorer gates remain closed. The reviewed source-closure proposal identifies seven additional executed/replay paths as a starting fifteen-path inventory, subject to transitive-import audit after wiring. Approval v2 already binds the manifest, reviewed HEAD, watchdog and child vectors, and review-report hash. Grant bindings also contain role entrypoints and watchdog/child start identities. These are not yet completely reconstructible from the frozen replay identity. Do not insert provisional hashes or relax exact roster equality to make the runner pass.

## Minimal launch-time attestation

Use one fixed leaf `<run_id>.launch-attestation.json` in the already pinned campaign-fit claims parent, **outside** the reserved run's receipt root. Add this leaf to the unused-run absence inventory and keep the watchdog claim as the first one-use claim. Only after the child reaches its stable runtime and while watchdog and child are still live, the watchdog captures their PID/start identity, command vector, resolved image path and digest, its own image/runtime identity, the pinned root and claim-parent device/inode, and the raw watchdog-claim SHA. Include protocol/run, manifest/approval/review hashes and reviewed HEAD. Use an exact canonical schema and bounded bytes; publish once with descriptor-relative `O_EXCL|O_NOFOLLOW`, file and parent-directory fsync, then canonical no-follow readback and file-identity verification. A failure consumes the run claim and sends no grant.

Freeze a **sidecar schema v1** with this exact top-level key set: `schema_version`, `protocol_id`, `run_id`, `manifest_sha256`, `approval_sha256`, `review_sha256`, `reviewed_git_head`, `watchdog_claim_sha256`, `physical_root`, `root_device`, `root_inode`, `receipt_root_relative`, `receipt_device`, `receipt_inode`, `claim_parent_device`, `claim_parent_inode`, `observed_monotonic_ns`, `watchdog_process`, and `child_process`. The two process objects have exact keys `pid`, `start_identity`, `argv`, `image_path`, and `image_sha256`; `child_process` additionally has `declared_launch_vector`, `declared_launch_image_path`, and `declared_launch_image_sha256`. Version is exactly integer 1; device/inode/PID/monotonic values are positive exact integers (not booleans); IDs and start identities are nonempty safe strings; SHA fields are lowercase 64-hex strings; paths are canonical absolute paths except the one fixed root-relative receipt path; argv and launch vector are nonempty bounded arrays of strings. The capture uses the existing process-start identity representation, with no new coercion from PID alone. Reject extra/missing keys, duplicate JSON keys, noncanonical encoding, oversized vectors or invalid path components. Serialize sorted-key compact ASCII JSON with no trailing bytes and a **64 KiB inclusive maximum**. The sidecar contains no grant secret or target data.

Retain the attestation's raw digest and file identity in watchdog memory before grant publication. A **distinct terminal schema v4** should bind that publication digest and identity in an exact `launch_attestation` object with keys `leaf`, `sha256`, `device`, `inode`, `mode`, and `size_bytes`, or JSON `null` when no sidecar was durably issued; v3 remains historical evidence for the already reviewed component and is not silently reinterpreted. `leaf` is exactly `<run_id>.launch-attestation.json`; digest is raw-byte SHA-256; the four stat fields are exact integers captured from the descriptor-open regular file. The publication/readback/replay identity tuple is exactly `(st_dev, st_ino, st_mode, st_size)` and all four values must match the terminal; no-follow open and a regular-file check are required. Require raw digest equality and stable stat before/after bounded read as well. The terminal writer must compare its final readback to the retained publication snapshot, never adopt a new digest from a late read. The existing ACK v1 must bind the exact v4 terminal bytes and file identity. The sidecar does not add a leaf to the receipt root, so `_write_grant_record()` can still require an empty root immediately before it writes `watchdog-child-grant.json`. **This does not satisfy campaign-fit's later empty-root check.** Campaign-fit currently rejects the grant leaf before its own claim; a separate, independently reviewed capability-bound exception allowing exactly that one pinned grant leaf is required before any production launch. The watchdog constructs `ABC6AuthorityBindings` from the frozen inputs plus the retained live attestation, then `GrantChannel.publish` rechecks live watchdog/child PID, start, vector and images against it before delivery. If the child exits or any identity changes between attestation and grant, do not send a grant; retain the consumed run and a truthful failure receipt. No retry under the same run ID.

On replay, open the claims parent and attestation with the pinned no-follow descriptors; require raw bytes, file identity and digest to match terminal v4. Before treating the watchdog claim as a source, require its **exact canonical schema** and compare its nested declared child launch vector, launcher/resolved image path and SHA, accepted argv forms, expected observed child image path/SHA, and watchdog command/image/runtime attestation to the frozen approval, manifest/runtime identity and the sidecar's live observations. Checking only the claim's raw hash or outer IDs is insufficient. Check sidecar claim hash against that separately verified claim and check all other source-backed fields against the frozen manifest, approval, review report, rooted path/device/inode and exact source/runtime/role contract. Construct the typed expected bindings only after these checks. Compare the expected object to the terminal, grant record and any child-side receipt; missing or contradictory evidence is `unreplayable`, never a defaulted field or trusted `failed` outcome. Do not resample a dead or reused PID to infer its former start identity. A contemporaneous sidecar is a process observation and provenance receipt, not an independent scientific replication or a defense against an actor who can rewrite the trusted checkout and all receipts.

Terminal-v4 replay distinguishes four preclaim states. **No child observed:** require `launch_attestation: null`, attestation leaf absent and no grant; preserve the existing structured prechild failure rules, including unstructured failure as `unreplayable`. **Child observed before durable attestation:** require no grant; absence or an incomplete/contradictory sidecar is `unreplayable`, regardless of a plausible terminal error. **Attestation issued, no grant:** verify the sidecar and absence of the grant record; classify only a separately structured and verified stop/failure with complete child/group cleanup, otherwise `unreplayable`. **Attestation and grant issued:** verify both distinct raw-byte links and the full expected-binding chain before any trusted classification. A grant without an attestation, a sidecar in the no-child branch, or any unexpected named leaf is `unreplayable`. All branches keep the run ID consumed; a later wake may inspect but never restart this claim.
